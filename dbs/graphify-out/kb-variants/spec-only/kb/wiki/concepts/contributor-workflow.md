# Contributor Workflow

The **contributor workflow** describes the main ways people can interact with the Ibex project to improve it: reporting bugs, asking questions, suggesting enhancements, and submitting code changes.

## Overview

In the licensing document, Ibex explicitly encourages community participation even though the license does not require it. The project asks users to:

- open a GitHub **issue** for bug reports, questions, or suggested improvements
- submit a **pull request** if they want to contribute code

This reflects a lightweight, open contribution model centered on public issue tracking and pull-request-based development.

## Key elements

### Issue reporting
Issues are the preferred channel for:

- bug reports
- questions
- feature suggestions
- general improvement ideas

This makes the issue tracker the main entry point for non-code participation.

### Code contributions
Pull requests are the expected mechanism for proposing code changes. This supports a review-based workflow where external contributors can propose fixes or enhancements for maintainers to evaluate.

### Community feedback
The document also notes that feedback is appreciated, even though it is not required by the license. This reinforces a collaborative project culture.

## Why it matters

A contributor workflow helps keep the project maintainable and community-friendly by providing clear paths for participation. For Ibex, the workflow is simple and direct:

- report problems in issues
- discuss ideas publicly
- contribute patches through pull requests
